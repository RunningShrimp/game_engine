# 版本政策 (Version Policy)

本文档定义游戏引擎项目的版本控制政策、API 稳定性保证和变更管理流程。

---

## 版本号规范

我们采用 [语义化版本 2.0.0 (Semantic Versioning 2.0.0)](https://semver.org/lang/zh-CN/)。

版本号格式：`MAJOR.MINOR.PATCH`

- **MAJOR (主版本号)**: 不兼容的 API 变更
- **MINOR (次版本号)**: 向后兼容的功能新增
- **PATCH (修订号)**: 向后兼容的问题修正

示例：`0.1.5`
- 主版本：0（开发阶段）
- 次版本：1
- 修订号：5

---

## 当前版本状态

### 主版本 0 (v0.x.x)

**状态**: 开发中 (Development)

**说明**:
- 主版本为 0 表示项目仍处于开发阶段
- API 可能频繁变化
- 不保证向后兼容性
- 适合早期采用者和实验性项目

**稳定性承诺**:
- **修订号 (PATCH)**: 向后兼容的错误修复
- **次版本号 (MINOR)**: 可能包含小的 API 变更
- **主版本号 (MAJOR)**: 重大架构变更或里程碑

**预计稳定版本**: v1.0.0 预计在 2025 Q4 发布

---

## API 稳定性级别

### 1. Stable (稳定)

**定义**: API 设计成熟，经过充分测试，生产环境可用。

**保证**:
- 除非主版本号增加，否则不会发生破坏性变更
- 破坏性变更必须经过：
  - 核心团队审查
  - 社区反馈期（至少 1 个月）
  - 迁移指南
  - 废弃周期（至少 2 个次版本）

**示例**: 核心渲染器、ECS 系统

---

### 2. Mature (成熟)

**定义**: 功能基本完整，API 设计较为稳定，可能有小幅调整。

**保证**:
- 破坏性变更只在次版本更新时发生
- 提供编译器级别的废弃警告
- 提供迁移指南

**示例**: 网络模块、音频系统

---

### 3. Experimental (实验性)

**定义**: 功能开发中，API 可能频繁变化，不建议生产环境使用。

**保证**:
- 不保证向后兼容性
- 可能在修订版本中发生 API 变更
- 变更记录在 API_STABILITY.md 中

**示例**:
- 光线追踪 (Ray Tracing)
- VXGI 全局光照
- GPU 物理加速
- GPU 流体模拟

**识别方法**:
- 模块级文档声明：`**API 稳定性**: 实验性 (Experimental)`
- 文档标记：`🚧` 图标

---

### 4. Deprecated (已弃用)

**定义**: 计划移除的 API，建议使用替代方案。

**流程**:
1. 标记为 `Deprecated`，发布废弃公告
2. 提供替代方案和迁移指南
3. 在至少 2 个次版本后移除
4. 移除时增加主版本号

**示例**: 旧的渲染 API（已替换为新的渲染管线）

---

## 变更管理流程

### 1. 破坏性变更 (Breaking Changes)

**定义**: 任何可能导致现有代码编译失败或运行时行为变化的变更。

**评估标准**:
- 公共 API 签名变更
- 行为语义变化
- 依赖项版本要求变化
- 配置格式变化

**处理流程**:

```
1. 提议阶段
   ├─ 创建 RFC (Request for Comments)
   ├─ 社区讨论 (至少 2 周)
   └─ 核心团队评估

2. 实施阶段
   ├─ 实现变更
   ├─ 添加废弃警告
   ├─ 编写迁移指南
   └─ 更新文档和测试

3. 发布阶段
   ├─ 在 CHANGELOG 中明确标注
   ├─ 发布公告邮件
   └─ 更新 API_STABILITY.md

4. 稳定化阶段
   ├─ 收集用户反馈
   ├─ 修复问题
   └─ 准备下一个版本
```

---

### 2. 功能新增 (Feature Additions)

**向后兼容的新功能**:
- 次版本号增加
- 不影响现有代码
- 可选使用

**实验性功能**:
- 标记为 `Experimental`
- 在 API_STABILITY.md 中追踪
- 功能稳定后升级为 `Mature` 或 `Stable`

---

### 3. 错误修复 (Bug Fixes)

**向后兼容的修复**:
- 修订号增加
- 不改变 API 签名
- 只修复错误行为

**行为变更**:
- 如果修复改变了可观察的行为，视为破坏性变更
- 需要按照破坏性变更流程处理

---

## 版本发布周期

### 开发阶段 (v0.x.x)

**周期**:
- 修订版本：每周（如有必要）
- 次版本：每 2-4 周
- 主版本：按里程碑

**流程**:
1. 功能开发分支
2. 代码审查
3. 测试验证
4. 发布候选 (RC)
5. 正式发布

---

### 稳定版本 (v1.0.0+)

**周期**:
- 修订版本：按需发布
- 次版本：每 1-3 个月
- 主版本：每 6-12 个月

**长期支持 (LTS)**:
- 主版本发布后提供至少 2 年的支持
- 安全修复持续 3 年
- LTS 版本：v1.x, v2.x, ...

---

## 废弃政策

### 废弃流程

```
v0.2.0: API 标记为 Deprecated
v0.3.0: 仍然可用，编译器警告
v0.4.0: 移除 API（主版本增加到 v1.0.0）
```

**例外情况**:
- 安全漏洞：立即移除
- 严重缺陷：可能在修订版中移除

---

## 依赖项管理

### 外部依赖版本

**策略**:
- 锁定关键依赖的主版本号
- 定期更新次要依赖
- 评估依赖的稳定性和安全性

**示例**:
```toml
[dependencies]
wgpu = "0.19"  # 锁定主版本
rapier3d = "0.17"  # 锁定主版本
tokio = { version = "1.35", optional = true }  # 可选依赖
```

### 依赖更新

**自动更新**:
- 每周检查安全更新
- 依赖机器人 (Dependabot) 自动 PR

**手动更新**:
- 次版本更新需要测试验证
- 主版本更新需要 RFC 和评估

## 测试和质量保证

### 测试覆盖率要求

| API 级别 | 测试覆盖率 | CI 要求 |
|----------|-----------|---------|
| Stable | > 90% | 必需 |
| Mature | > 80% | 必需 |
| Experimental | > 60% | 推荐 |
| Deprecated | 现有测试 | 可选 |

---

### 持续集成 (CI)

每个 PR 必须通过：
- 单元测试
- 集成测试
- 代码格式检查
- Clippy 警告检查
- 文档构建

## 特殊情况

### 安全漏洞

**策略**:
- 立即发布修复版本
- 可能跳过正常流程
- 跨所有受支持版本发布
- 安全公告邮件

### 关键缺陷

**策略**:
- 快速发布修复版本
- 评估是否需要破坏性变更
- 提供变通方案（如果可能）

## 版本号示例

### 正常开发周期

```
v0.1.0 → v0.1.1 → v0.1.2 → v0.2.0 → v0.2.1 → v0.3.0 → v1.0.0
 修复    修复    新增   破坏性  修复   稳定    稳定版
```

```
v0.1.0: RayTracing API 引入 (Experimental)
v0.2.0: API 重新设计 (仍为 Experimental)
v0.3.0: 功能完整，升级为 Mature
v1.0.0: 首个稳定版本
```
