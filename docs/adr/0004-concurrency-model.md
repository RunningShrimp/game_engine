# ADR-0004: 并发模型选择

## 状态
已接受

## 日期
2025-01-23

## 背景

游戏引擎需要高效利用多核 CPU 来处理并发任务：

1. **物理模拟**：需要独立线程运行，避免阻塞渲染
2. **资源加载**：异步 I/O 操作不应阻塞主线程
3. **网络通信**：需要异步处理消息
4. **AI 计算**：路径寻找等计算密集型任务可以并行

## 决策

采用 **混合并发模型**，结合 Rust 的 async/await 和传统线程池。

### 并发架构

#### Async/Await (异步编程)

使用 Tokio 作为异步运行时：
- **资源加载**：协程加载器支持异步资源加载
- **网络 I/O**：TCP/UDP 连接使用异步操作
- **着色器编译**：后台异步编译避免阻塞

#### 线程池

使用专用线程处理计算密集型任务：
- **物理模拟**：独立线程运行物理步进，使用双缓冲同步
- **并行消息处理**：使用 `rayon` 并行处理网络消息
- **GPU 计算**：独立的 GPU 计算任务调度

#### 消息队列

使用通道 (Channel) 实现线程间通信：
- `crossbeam_channel`：无锁高性能通道
- `tokio::sync::mpsc`：异步通道

### 技术选型

| 组件 | 技术 | 原因 |
|--------|------|------|
| 异步运行时 | Tokio | 成熟、高性能、生态系统完善 |
| 并行处理 | Rayon | 数据并行、易用 |
| 线程间通信 | crossbeam | 无锁、高性能 |

## 后果

### 正面影响

1. **高并发性能**：充分利用多核 CPU
2. **非阻塞 I/O**：异步 I/O 不阻塞主线程
3. **可扩展性**：任务可以轻松分发到不同线程
4. **类型安全**：Rust 的类型系统确保线程安全

### 负面影响

1. **复杂性**：异步代码比同步代码更复杂
2. **调试难度**：异步代码调试更困难
3. **运行时开销**：异步运行时有少量开销

## 替代方案

### 方案 A：完全同步模型
- **优点**：简单，易于理解和调试
- **缺点**：无法充分利用多核 CPU
- **未被选择的原因**：性能受限

### 方案 B：完全异步模型
- **优点**：一致的异步风格
- **缺点**：计算密集型任务使用异步会增加开销
- **未被选择的原因**：物理模拟等任务更适合专用线程
