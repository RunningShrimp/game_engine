# ADR-0002: 应用领域驱动设计

## 状态
已接受

## 日期
2025-01-23

## 背景

游戏引擎作为一个通用框架，不应包含任何业务逻辑。然而，为了确保引擎的长期可维护性和可扩展性，需要一种架构模式来：

1. **封装业务规则**：游戏特定的逻辑应封装在领域对象中
2. **避免贫血模型**：数据和行为应共同封装，避免只有数据的"贫血"对象
3. **明确领域边界**：物理、音频、渲染等领域的边界应清晰

## 决策

应用 **领域驱动设计 (DDD)** 原则到引擎架构中。

### 领域模型设计

- **富领域对象**：领域对象包含数据和行为（如 `RigidBody` 包含质量、速度和移动逻辑）
- **领域服务**：跨聚合的业务逻辑（如 `PhysicsDomainService` 管理物理世界）
- **值对象**：不可变的值类型（如 `Position`、`Velocity`）
- **聚合根**：控制领域对象的访问（如 `Scene` 是场景中所有实体的聚合根）

### 技术实现

- 使用 Rust trait 定义领域对象接口
- 使用模块化组织领域层 (`src/domain/`)
- 实现领域事件系统用于解耦

## 后果

### 正面影响

1. **可维护性**：业务逻辑集中在领域对象中，易于理解和修改
2. **可测试性**：领域对象可以独立测试，不依赖外部框架
3. **可扩展性**：添加新功能时，可以在领域层找到合适的放置位置
4. **代码清晰**：通过富领域对象避免贫血模型反模式

### 负面影响

1. **初始复杂性**：需要设计和实现更多类型和接口
2. **学习曲线**：开发人员需要理解 DDD 概念
3. **潜在过度设计**：对于简单场景，可能引入不必要的复杂性

## 替代方案

### 方案 A：贫血领域模型
- **优点**：实现简单，学习曲线低
- **缺点**：业务逻辑分散，难以维护
- **未被选择的原因**：违反 DDD 最佳实践，长期维护困难

### 方案 B：无特定领域层
- **优点**：更简单的架构
- **缺点**：缺乏清晰的边界，难以扩展
- **未被选择的原因**：不符合通用游戏引擎的架构需求
