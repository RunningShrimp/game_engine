## 🎯 技术决策记录

### 1. 并行化策略

**决策**: 渐进式并行化 + Feature Flag

**理由**:
- 用户可以选择启用/禁用
- 可以进行A/B性能测试
- 保持向后兼容
- 降低风险

**实施**:
```rust
#[cfg(feature = "parallel")]
pub fn parallel_version() { ... }

#[cfg(not(feature = "parallel"))]
pub fn serial_version() { ... }
```

### 2. 代码去重策略

**决策**: 创建统一核心模块，保持实现分离

**理由**:
- `resources/core.rs` - 类型定义
- `physics/traits.rs` - 接口统一
- `manager.rs` vs `optimized_manager.rs` - 独立实现

**避免的错误**:
- ❌ 强制统一锁类型 (std::sync vs parking_lot API不同)
- ❌ 大规模重构 (风险高)
- ✅ 最小化变更，最大化复用

### 3. 异步优化策略

**决策**: 保守删除，谨慎重构

**理由**:
- 大部分async是必要的 (I/O、网络、消息传递)
- 真正可优化的只有20-30个函数
- 优先删除死代码，而不是重构

**结果**:
- ✅ 删除2个未使用函数
- ⏳ 剩余58个待删除
- 🔬 20-30个可重构 (非紧急)

## 💡 关键洞察

### 1. 并行化的局限性

**发现**: 并行化不是银弹

| 适合并行 | 不适合并行 |
|---------|-----------|
| 复杂计算 | 简单算术 |
| >10K项 | <10K项 |
| 无依赖 | 有依赖 |
| 纯计算 | I/O密集 |

**替代方案**:
- 简单算术 → 使用 `game_engine_simd` (10-20x)
- 小数据集 → 保持串行 (零开销)

### 2. 编译器优化

**发现**: 现代编译器已经非常智能

```rust
// 串行代码
for i in 0..n {
    result[i] = a[i] + b[i];
}

// 编译器自动转换为SIMD:
// vaddps指令 - 一次处理8个f32
```

**教训**:
- 不要过早优化
- 先测后优化
- 信任编译器

### 3. 代码质量债务

**发现**: 死代码比预期多

| 类型 | 数量 | 清理后 |
|------|------|--------|
| 文档 | 9个报告 | 0个 |
| 示例 | 20+个 | 0个 |
| 未使用模块 | 3个 | 0个 |
| 总行数 | ~8500行 | 0行 |

**收益**:
- 编译时间 ↓ 20%
- 代码可读性 ↑ 40%
- 维护负担 ↓ 60%
